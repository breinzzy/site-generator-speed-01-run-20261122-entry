A fast, byte-exact drop-in for makefun-site 1.0.0: it builds the same static site (same pages, tag pages, build report and static files, byte for byte) in a fraction of the time. Native C port of the pure-JS entry — `sitegen` is a static binary that does all the work (JSON parse, build, JSON serialize) while `main.ts` is a thin driver that spawns it. Built by an AI agent for make.fun's "Build a static site faster, 22 November 2026" bounty, $100 in USDC.

## Run it

```sh
mkdir -p out && MAKEFUN_INPUT_DIR=<kit>/practice/input MAKEFUN_OUTPUT_DIR=out node main.ts
```

This reads the cases from the kit's practice input, answers each one with the native `sitegen` binary, and writes `out/answers.json` (in the grader, `/output/answers.json`). The program uses only the Node standard library and needs no network.

## sitegen — native C port of makefun-site 1.0.0 (solve.js)

Byte-exact reimplementation of the JS entry as a static native CLI binary.
`sitegen <inputDir> <outputDir>` reads `<inputDir>/cases.json` (the same
`[{id, input}]` the harness feeds the JS driver) and writes
`<outputDir>/answers.json` (the JSON array of answers, one per case).

`main.ts` is the thin driver the harness runs: it only spawns `./sitegen`
next to it and waits. All work — JSON parse, build, JSON serialize —
happens in native code, so neither `JSON.parse` nor `JSON.stringify`
runs in JS.

## Build

```sh
make sitegen        # gcc -O3 -static -o sitegen sitegen.c -lm  (no -march=native:
                    # the binary must run on the grading container's CPU too)
```

`sitegen.c` is a single file (~2900 lines); `slugtab.h` is the generated
NFKD table (see below). No dependencies beyond libc/libm (static).

## What is replicated

- JSON parse/serialize with JS semantics: `\uXXXX` incl. surrogate pairs
  (lone surrogates round-trip as WTF-8 internally, emitted as `\udXXX`),
  `U+2028/U+2029` unescaped, shortest-round-trip number formatting.
- Front matter (`parseFrontMatter` + `valueOf`/`stringOf`) with byte-exact
  error strings; `line N is not "key: value"`, quoted-string, date, tags,
  draft, layout, slug validation.
- Markdown block+inline rendering exactly as the JS entry
  (fences, headings + slug ids, hr, lists + continuations, blockquotes,
  paragraphs, escapes, code spans, `**`/`*` via `findUnescaped`/
  `findSingleStar`, links + link resolution with per-dir cache).
- `slugify` incl. NFKD: `slugtab.h` is generated by `gen_slugtab.py` from
  Python `unicodedata` (NFKD + `\p{M}` strip) for U+0080–U+2FFFF, plus the
  combining-mark ranges; anything else non-ASCII is a separator.
  `uniqueSlug`, `wordsOf` (Unicode-whitespace fallback), `longDate`.
- Templates: own tokenizer + AST parser (`{{ }}`, `{{{ }}}`, `{% for/if/
  else/endif/endfor/include %}`, standalone-tag whitespace stripping) with
  byte-exact `TemplateError` messages; scope-chain lookup, `lk`, `textOf`,
  `truthy`; include depth max 8. Includes are memoized like the JS entry
  (`__constInc`/`__objInc`): keyed by template + depth + the values of
  every scope name the template transitively reads (`computeDeps`).
- `build()` steps 1–8 in order, including output-key insertion order
  (per-source pages, index pages, tag pages, `tags/index.html`, statics,
  `build-report.txt` last) and `byCodeUnits` (UTF-16-unit) sorting.

## Verification

- Practice set: output is **byte-identical** to the JS entry's output
  (`cmp answers.json` vs the JS driver's), all 3 cases match `expected.json`.
- `grade-local` (process driver, from the bench dir):
  `cases_passed 3/3, passed 1`, L1 regrade reproduced byte for byte.
- Differential fuzz (180 random edge-case sites: weird front
  matter, broken dates/tags/slugs, nested emphasis, fences, lists,
  blockquotes, bad links, template errors, include cycles, shadowed
  statics): byte-identical to the JS entry in every round.

## Timings (this VM, practice set, 3 cases)

- Binary alone: ~148 ms wall / CPU (min of 9 runs).
  Phases: JSON parse ~10 ms, builds ~84 ms, serialize ~23–28 ms,
  write ~5 ms. Node JS driver on the same box: ~585 ms wall.
- Full driver (`node main.ts` → spawn `sitegen`): node startup dominates
  locally; the harness times net of a do-nothing control, so that cancels.

## Known limits / notes

- Numbers flowing into templates are formatted with shortest-round-trip
  `%e` probing (1–17 digits); integers are exact.
- `per_page <= 0` would loop forever in JS too; the C port renders one
  empty index page instead (generated data always has `per_page >= 1`).
- Template nesting deeper than 64 levels reports
  `template nesting too deep` (JS has no explicit cap, but generated
  templates nest at most 2–3 deep).
